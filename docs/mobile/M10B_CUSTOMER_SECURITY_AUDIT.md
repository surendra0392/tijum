## 1. SECURITY POSTURE OVERVIEW

The TIJUM Customer Native Mobile Application handles sensitive marketplace operations, including user identity, payment authorization, financial refunds, and dispute redressal. This audit reviews the architecture, code implementation, and network contracts against industry best practices (OWASP Mobile Application Security Verification Standard - MASVS) and TIJUM foundational security rules.

---

## 2. AUDIT EVALUATION ACROSS KEY SECURITY DOMAINS

### 2.1 Single Active Session Architecture & Role Isolation
- **Secure Storage:** Tokens are persisted using `Expo SecureStore` (hardware-backed Android Keystore / iOS Keychain). Plain text `AsyncStorage` is strictly forbidden for authentication credentials.
- **Principal Separation:** Two distinct keys are stored: `tijum_active_session_token` and `tijum_active_principal_type`. Customer sessions cannot access partner (`owner/*`) or admin endpoints.
- **Immediate Invalidation:** Calling `/api/v1/auth/logout` deletes the active personal access token from Laravel Sanctum and purges the local secure store.

### 2.2 Customer Protection Case Authorization
- **Access Control:** `CustomerProtectionController@show` and `addMessage` enforce strict customer ownership:
  ```php
  $case = CustomerProtectionCase::query()
      ->where('case_reference', $reference)
      ->where('user_id', $user->id)
      ->first();
  ```
  Attempting to access or append messages to another customer's case results in an immediate `404 Not Found`, preventing IDOR (Insecure Direct Object Reference) vulnerabilities.
- **Message Content Sanitization:** Messages are validated (`min:2`, `max:3000`), stripped of executable tags, and escaped during rendering to prevent stored XSS and payload injections.
- **Internal Note Isolation:** Internal staff notes (`is_internal = true`) are strictly filtered out on the backend and never serialized to the customer client.

### 2.3 Payment Verification & Signature Integrity
- **Native Razorpay Checkout:** Orders are authoritatively generated by backend `CreateRazorpayOrder` action. The client does not dictate prices, minor units, or fees.
- **Server-Side Cryptographic Verification:** All payment completions must be submitted to `POST /api/v1/customer/reservations/{ref}/payment/verify` with `razorpay_order_id`, `razorpay_payment_id`, and `razorpay_signature`. The backend validates the HMAC-SHA256 signature using the secret key before confirming inventory allocation.
- **15-Minute Hold Window:** Inventory holds automatically expire after 15 minutes, preventing inventory lockup and denial-of-service attacks by malicious actors.

### 2.4 Cancellation, Refund & Banking Details Security
- **Lifecycle Protection:** Reservations can only be cancelled by customers if in a cancellable state (`awaiting_payment`, `payment_pending`, `confirmed` prior to check-in).
- **Masking of Banking Data:** Only non-sensitive bank references (UTR / RRN) and gateway IDs are serialized to the client. Full account numbers or payment instrument credentials are never transmitted.

### 2.5 Input Validation & Form Boundaries
- **Reviews:** Overall ratings must fall strictly within the 1–5 range. Feedback content requires a minimum of 10 characters if provided, preventing review spam. Only verified completed stays are eligible for reviews.
- **Password Changes:** Updating customer passwords requires verification of the `current_password` and confirmation matching, preventing unauthorized session takeover.
- **Promotion Quotes:** Coupon codes are checked against database records for validity, date ranges, minimum order minor units, category restrictions, and single-use constraints.

---

## 3. AUDIT CONCLUSION & READINESS STATEMENT

The TIJUM Customer Native Mobile Application and its associated REST API V1 endpoints exhibit robust defense-in-depth security. No high-risk or critical vulnerabilities were discovered. All endpoints enforce strict user ownership, input validation, cryptographic verification, and principle of least privilege.
